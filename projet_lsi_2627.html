Projet Conduit

Author

Mikaël Valot

1 Introduction

Le site RealWorld propose différentes implémentations du même logiciel de blogging, Conduit, qui est similaire à Medium. Cela permet de comparer différentes stacks technologiques sur un projet réaliste.

Vous pouvez tester le frontend ici sans installation : Demo Conduit Vue3

Notre projet consiste à améliorer ce logiciel avec des corrections de bugs et des nouvelles fonctionnalités. Nous utiliserons :

  • un frontend Vue.js, dérivé de Vue.js + Vite. C’est le même frontend que pour le projet Java Spring Boot (ALTN72).
  • un backend Scala 3 / ZIO, dérivé de zio-conduit-doobie

Le backend utilise les bibliothèques suivantes :

  • ZIO : système d’effets fonctionnel, injection de dépendances avec ZLayer
  • ZIO HTTP : serveur HTTP et routes de l’API REST
  • Doobie : accès fonctionnel à la base de données en SQL
  • Flyway : migrations du schéma de la base PostgreSQL
  • Circe : sérialisation JSON
  • ZIO Test : tests unitaires et tests par propriétés (générateurs)

2 Objectifs pédagogiques

  • Savoir se repérer dans une base de code existante et la faire évoluer.
    • Il est rare en entreprise de démarrer un nouveau projet “from scratch”.
  • Observer et intégrer les bonnes pratiques de programmation fonctionnelle en naviguant dans ce code : immutabilité, fonctions pures, effets, erreurs typées, types forts pour le domaine.
  • Comparer avec l’implémentation Spring Boot du même logiciel : avantages et inconvénients de chaque paradigme.
  • Développer de nouvelles fonctionnalités en respectant le style du code existant et les principes de la clean architecture.
  • Écrire des tests en utilisant des générateurs et mesurer la couverture de code.

3 Architecture

Le code est organisé en trois couches. Le README_original.md du projet les décrit en détail.

src/main/scala/conduit/
├── application/      # couche application : point d'entrée HTTP, migrations
│   └── http/         #   routes, middlewares, codecs JSON
├── domain/           # couche domaine : ne dépend d'aucune bibliothèque technique
│   ├── model/        #   entités, types, requêtes, réponses, erreurs
│   ├── logic/        #   interfaces (traits) : repositories, entrypoints, autorisations...
│   └── service/      #   implémentations des règles métier
└── infrastructure/   # couche infrastructure : implémentations techniques des interfaces
    ├── postgres/     #   repositories Doobie / PostgreSQL
    ├── inmemory/     #   repositories en mémoire
    └── opentelemetry/#   supervision

Le traitement d’une requête traverse les couches dans cet ordre : route (application/http/route) → entrypoint (domain/service/entrypoint) → validation, autorisation → repositories (infrastructure/postgres/repository).

4 Déroulement du projet

Trois séances, en binômes.

  • séance 1 (semaine 46) : découverte du code, corrections des premiers bugs
  • séance 2 (semaine 48) : séance plus courte pour faire la 2ème évaluation (20 %), développement des fonctionnalités plus avancées
  • séance 3 (semaine 48) : développement des fonctionnalités, puis DE de projet
  • Rendu final pour le 20/12 23:59

5 Critères d’évaluation

  • 60% DE de projet : questions sur les fonctionnalités développées
    • évalue la compréhension et la prise de recul
    • vous devez comprendre le code que votre binôme a réalisé
    • plus équitable qu’une soutenance : tout le monde a les mêmes questions, je peux comparer les réponses
    • permet de passer plus de temps sur le projet
  • 40% Rendu
    • fonctionnalités couvertes
    • réponses dans le README.md
    • code coverage
    • code quality
    • qualité des commits
      • commentaires
      • commit du test qui échoue avant le commit du code de prod
      • pas trop de code modifié en une seule fois

7 Travail à réaliser

Pour chaque bug ou fonctionnalité :

  1. écrivez un test qui échoue, committez
  2. écrivez le code de production qui fait passer le test, committez
  3. répondez aux questions dans le README.md

7.1 VALIDATION : règles sur les tags

Créez un article avec des tags. Aujourd’hui, seul un tag vide est refusé : on peut créer des tags comme Hello World!!! ou scala et Scala, qui sont deux tags différents.

Ajoutez deux règles de validation :

  • un tag ne contient que des lettres minuscules, des chiffres et des tirets (par exemple cats-effect, scala3)
  • un article a au plus 5 tags

Ces deux règles ne se placent pas au même endroit dans le code. Cherchez où est faite la vérification du tag vide, puis demandez-vous si la deuxième règle porte sur un tag ou sur un article.

  • Toutes les erreurs doivent être renvoyées en une seule fois : un article avec 6 tags dont un invalide renvoie deux erreurs. Voir Validation.
  • Testez vos règles avec des tests unitaires
  • Vérifiez dans le navigateur que le frontend affiche bien les erreurs.

BONUS : Testez les règles avec des Générateurs : générez des tags valides, vérifiez qu’ils sont acceptés. Générez des tags invalides, vérifiez qu’ils sont rejetés.

7.2 BUG : TagRepository

Dans TagRepositorySpec, le test « Add tags and retrieve them » appelle addTagsAndRetrieveThem avec une liste fixe de deux tags. Modifiez-le avec check pour qu’il vérifie la même chose avec n’importe quelle liste de tags générée. Il vous faudra écrire un générateur de tags.

  1. Lancez le test. ZIO Test trouve un contre-exemple qui fait échouer le test : lequel ?
  2. Corrigez le bug
  3. Répondez dans le README.md :
    • pourquoi les tests de CommentEntrypointServiceSpec, qui utilisent les repositories en mémoire, n’auraient pas trouvé ce bug ?
    • est-ce qu’on peut reproduire ce bug avec l’interface ?
    • qu’apporte check par rapport à un test écrit avec quelques exemples choisis à la main ?

7.3 FEATURE : Modifier un commentaire

On peut créer ou supprimer ses commentaires, mais on ne peut pas les éditer. Modifiez le backend et le frontend pour le permettre. Si vous avez déjà réalisé cette fonctionnalité dans le projet ALTN72, vous pouvez réutiliser votre frontend.

  • La route est PUT /api/articles/:slug/comments/:id, avec le même corps JSON que la création
  • ⚠️ Attention aux droits : seul l’auteur d’un commentaire peut le modifier
  • Suivez le parcours d’une requête : chaque couche a quelque chose à ajouter. N’oubliez pas l’implémentation en mémoire du repository.
  • Ajoutez les tests correspondants
  • Répondez dans le README.md : le slug de l’article présent dans l’URL est-il vérifié lors de la suppression d’un commentaire ? Que se passe-t-il si on appelle DELETE /api/articles/un-autre-article/comments/:id ? Faites en sorte que la modification ne présente pas ce problème.

BONUS

L’utilisateur essaie de modifier le même commentaire en ayant deux navigateurs ouverts.

  • Décrivez dans le README.md le problème que cela peut poser
  • Corrigez le problème

7.4 FEATURE : Rôles

  1. Ajoutez un rôle aux utilisateurs. Ils peuvent avoir l’un de ces rôles :

    • writer : rôle par défaut, mêmes droits que maintenant.
    • moderator : writer + peut modifier/supprimer les articles et commentaires de tout le monde.
    • admin : moderator + peut changer les rôles des utilisateurs

  2. Modifiez le schéma de la base avec une nouvelle migration Flyway (V2__...sql), et mettez des rôles aux utilisateurs des données d’exemple (R__seed_data.sql)

  3. Affichez le rôle dans l’écran Settings

  4. Ajoutez un écran de gestion des utilisateurs pour l’admin

    • l’écran liste tous les utilisateurs
    • on peut cliquer sur un utilisateur pour aller sur l’écran des settings
    • dans Settings, l’admin peut modifier le rôle

  5. Le rôle est enregistré en base de données. Au moment de vérifier les droits d’un utilisateur, faut-il relire son rôle en base, ou le copier dans le token JWT au moment du login (voir TokenAuthenticationService) ?

    • Écrivez vos réflexions dans le README.md.
    • Que se passe-t-il dans chaque cas quand un admin retire le rôle moderator à un utilisateur connecté ?

  6. Modifiez l’UI et les services d’autorisation (domain/service/authorisation) pour autoriser/interdire les opérations correspondant à chaque rôle

8 Conseils et bonnes pratiques

  • Pratiquez le TDD dans la mesure du possible : écrivez d’abord un test qui échoue, committez, puis écrivez le code de production.
  • Inspirez-vous des tests existants (src/test/scala) : ils montrent comment construire les données de test avec des générateurs et comment tester un service ou une route.
  • Avant de modifier une fonctionnalité, suivez le chemin d’une requête dans les trois couches.
  • Lisez les types : la signature ZIO[R, E, A] d’une méthode indique ce dont elle a besoin (R), comment elle peut échouer (E) et ce qu’elle renvoie (A).
  • Vous serez évalués sur la partie backend. Ne passez pas trop de temps à faire un joli frontend.
  • Vous pouvez utiliser une IA, mais vous devez comprendre le code produit et pouvoir le justifier (voir Usage des IA).
