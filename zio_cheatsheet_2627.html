ZIO Cheat Sheet - Projet Conduit

Author

Mikaël Valot

Ce document présente les éléments clés pour lire et modifier le code du projet Conduit. Il ne remplace pas la documentation de ZIO : il montre seulement les patterns que vous rencontrerez dans le projet, avec des exemples tirés du code.

1 Le type ZIO[R, E, A]

Une valeur de type ZIO[R, E, A] est la description d’un programme, qui :

  • a besoin d’un environnement R pour s’exécuter (des services, une transaction…)
  • peut échouer avec une erreur de type E
  • peut réussir avec une valeur de type A

Créer un ZIO n’exécute rien : c’est une valeur immuable, qu’on peut combiner avec d’autres. Le programme n’est exécuté qu’une seule fois, au démarrage de l’application (Main) ou d’un test.

ZIO.succeed(42)                // ZIO[Any, Nothing, Int]   : réussit toujours
ZIO.fail(NotFound.user(id))    // ZIO[Any, NotFound, Nothing] : échoue toujours
ZIO.unit                       // ZIO[Any, Nothing, Unit]

Any en position R signifie « n’a besoin de rien », Nothing en position E signifie « ne peut pas échouer ».

Le projet définit des alias pour rendre les signatures plus lisibles, par exemple :

trait CommentRepository {
  protected type Result[A] = ZIO[Transaction, PersistenceError, A]

  def find(commentId: CommentId): Result[Option[Comment]]
  def save(comment: Comment.Data): Result[Comment]
}

Lisez les types : la signature d’une méthode indique ce dont elle a besoin, comment elle peut échouer et ce qu’elle renvoie.

2 Enchaîner des effets : for-comprehension

On enchaîne des ZIO avec une for-comprehension, comme pour Option ou Either :

for {
  validated <- validation.parse(request).validOrFail       // <- : exécute un effet et récupère son résultat
  slug       = validated.slug                              // =  : simple valeur, pas d'effet
  articleId <- permalinks.resolve(slug) ?! NotFound.article(slug)
  comment   <- comments.save(Comment.Data(articleId, validated.body, validated.author))
} yield GetCommentResponse.make(comment, author, following)
  • Les étapes s’exécutent dans l’ordre.
  • Si une étape échoue, les suivantes ne sont pas exécutées : l’erreur est propagée (comme une exception, mais visible dans le type).
  • Le type R du résultat combine les besoins de chaque étape, et le type E combine leurs erreurs.

Autres opérations utiles :

effect.map(f)                  // transforme la valeur de succès
effect.flatMap(a => other(a))  // ce qu'utilise la for-comprehension
effect1 *> effect2             // exécute effect1, ignore son résultat, puis exécute effect2
ZIO.foreach(list)(a => f(a))   // exécute un effet pour chaque élément, renvoie la liste des résultats

ZIO.foreach fonctionne aussi sur une Option : l’effet est exécuté seulement si l’Option contient une valeur. Exemple tiré de CommentEntrypointService.listComments, où l’utilisateur peut ne pas être connecté :

val userId: Option[UserId] = request.requester.option.map(_.userId)   // None si non connecté

// ZIO.foreach(userId)(...) : ZIO[Transaction, PersistenceError, Option[List[AuthorId]]]
//   - None    : aucune requête, résultat None
//   - Some(id): exécute followers.list(id, authorIds), résultat Some(auteurs suivis)
followed <- ZIO.foreach(userId)(id => followers.list(id, authorIds)).map(_.getOrElse(Nil))

3 Erreurs typées

3.1 Hiérarchie des erreurs

Toutes les erreurs métier étendent ApplicationError (domain/model/error). Ce ne sont pas des exceptions : on ne les lance pas avec throw, on les renvoie avec ZIO.fail.

trait ApplicationError:
  def message: String

object ApplicationError:
  trait NotFoundError     extends ApplicationError
  trait UnauthorisedError extends ApplicationError
  trait ValidationError   extends DomainError
  ...

Le type E peut être une union d’erreurs : ZIO[R, PersistenceError | NotFound, A].

Dans la couche HTTP, ErrorMiddleware transforme chaque catégorie d’erreur en code HTTP : NotFoundError → 404, UnauthorisedError → 403, InvalidInput (validation) → 400, le reste → 500.

3.2 Opérateurs sur les erreurs

effect.mapError(e => OtherError(e))      // transforme l'erreur
effect.someOrFail(NotFound.user(id))     // ZIO[R, E, Option[A]] => ZIO[R, E | NotFound, A]
effect.orDie                             // erreur "impossible" : transforme l'erreur en défaut (crash)
effect.flip                              // inverse succès et erreur (utile dans les tests)

Le projet définit l’opérateur ?! comme raccourci de someOrFail (voir EntrypointDsl) :

articleId <- permalinks.resolve(slug) ?! NotFound.article(slug)
// si resolve renvoie None, le programme échoue avec NotFound.article(slug)

4 Types du domaine et validation

4.1 Subtype

Plutôt que des Long et des String partout, le domaine utilise des types dédiés, définis avec Subtype de ZIO Prelude :

type CommentId = CommentId.Type
object CommentId extends Subtype[Long]

val id: CommentId = CommentId(42L)   // construction
val n: Long       = id               // un CommentId EST un Long (Subtype)

Le compilateur empêche alors de passer un ArticleId là où on attend un CommentId. À l’exécution, il n’y a aucun surcoût : un CommentId est un simple Long.

4.2 Validation

Validation[E, A] (ZIO Prelude) ressemble à Either[E, A], mais accumule les erreurs au lieu de s’arrêter à la première. Voir le cours : CM5 - Le type Validation.

Exemple du projet :

object CommentBody extends Subtype[String] {
  def validated(body: String): Validation[Error, CommentBody] =
    Validation
      .validate(validateIsNotTooShort(body), validateIsNotTooLong(body))
      .map(_ => CommentBody(body))
}

Les services de validation (domain/service/validation) transforment une requête brute en données typées. Dans les entrypoints, validOrFail convertit une Validation en ZIO qui échoue avec InvalidInput (la liste de toutes les erreurs) :

validated <- validation.parse(request).validOrFail

5 Services et injection de dépendances avec ZLayer

5.1 Un service

Un service est un trait (l’interface, dans domain/logic) et une classe qui l’implémente (dans domain/service ou infrastructure). Les dépendances sont passées au constructeur. Par exemple, CommentEntrypointService a besoin de plusieurs autres services :

class CommentEntrypointService(
  unitOfWork: UnitOfWork,
  authorisation: CommentAuthorisation,
  validation: CommentValidator,
  comments: CommentRepository,
  ...
) extends CommentEntrypoint

5.2 Un ZLayer

Un ZLayer[RIn, E, ROut] est une recette pour construire le service ROut à partir des services RIn. Chaque service a un layer dans son objet compagnon, qui récupère ses dépendances avec ZIO.service puis appelle le constructeur :

object CommentEntrypointService:
  val layer: ZLayer[UnitOfWork & CommentAuthorisation & CommentValidator & CommentRepository & ...,
                    Nothing,
                    CommentEntrypointService] =
    ZLayer {
      for {
        unitOfWork    <- ZIO.service[UnitOfWork]            // récupère un service de l'environnement
        authorisation <- ZIO.service[CommentAuthorisation]
        validator     <- ZIO.service[CommentValidator]
        comments      <- ZIO.service[CommentRepository]
        ...
      } yield CommentEntrypointService(unitOfWork, authorisation, validator, comments, ...)
    }

Le type RIn (UnitOfWork & CommentAuthorisation & ...) liste les dépendances : le layer ne peut être construit que si on lui fournit tous ces services.

Ces dépendances ont elles-mêmes des dépendances. Pour une requête sur les commentaires :

CommentRoutes ──► CommentEntrypoint ──► CommentAuthorisation ──► CommentRepository
                        │                                              ▲
                        ├──► CommentValidator (aucune dépendance)      │
                        └──► CommentRepository ────────────────────────┘

Un service sans dépendance utilise ZLayer.succeed :

object CommentValidationService:
  val layer: ZLayer[Any, Nothing, CommentValidator] = ZLayer.succeed(CommentValidationService())

5.3 Assembler les layers

layerA ++ layerB     // fournit les services de layerA et de layerB
layerA >>> layerB    // layerA fournit les dépendances de layerB

Exemple dans PostgresModule :

object PostgresModule {
  // ZLayer[DatabaseSourceConfig, Nothing, HikariDataSource] : pool de connexions, construit à partir de la configuration,
  // et fermé automatiquement à l'arrêt de l'application (withFinalizerAuto)
  val datasource = ZLayer.scoped:
    ZIO.service[DatabaseSourceConfig].map(config => new HikariDataSource(config.toHikariConfig)).withFinalizerAuto

  // >>> : le pool de connexions est fourni à PostgresUnitOfWork, qui en a besoin pour ouvrir les transactions
  val unitOfWork = datasource >>> PostgresUnitOfWork.layer

  // ++ : le module fournit tous les repositories, le UnitOfWork et le pool de connexions
  val layer      = PostgresRepositoryModule.layer ++ unitOfWork ++ datasource
}

Et InMemoryRepositoryModule regroupe tous les repositories en mémoire avec ++ :

val layer =
  InMemoryUnitOfWork.layer ++
    InMemoryUserRepository.layer ++
    InMemoryCommentRepository.layer ++
    ...

En pratique, on donne simplement la liste des layers à .provide(...) : ZIO trouve tout seul dans quel ordre les construire, et construit une seule instance de chaque service, partagée par tous ceux qui en dépendent (ici, le même CommentRepository pour l’entrypoint et l’autorisation).

Exemple dans CommentEntrypointServiceSpec, où l’ordre des layers n’a pas d’importance :

spec.provide(
  CommentEntrypointService.layer,       // a besoin de CommentAuthorisation, CommentValidator, repositories...
  CommentValidationService.layer,       // aucune dépendance
  CommentAuthorisationService.layer,    // a besoin de CommentRepository
  InMemoryRepositoryModule.layer,       // fournit les repositories et UnitOfWork (en mémoire)
)

Les modules (DomainServiceModule, PostgresModule, InMemoryModule…) regroupent les layers d’une couche. Les modes de lancement (HttpApplication.dev, inmemory…) les assemblent de la même façon. Pour passer de PostgreSQL à la mémoire, il suffit de remplacer PostgresModule.layer par InMemoryModule.layer : les services du domaine ne changent pas.

provide vérifie à la compilation que toutes les dépendances sont fournies. Si vous ajoutez une dépendance à un service, le message d’erreur indique le layer manquant.

C’est l’équivalent de l’injection de dépendances de Spring, mais vérifié par le compilateur, sans annotations ni réflexion.

6 Transactions

Les méthodes des repositories renvoient un ZIO[Transaction, ...] : elles ont besoin d’une transaction ouverte pour s’exécuter. Seul UnitOfWork.execute peut fournir cette transaction : il l’ouvre, exécute le programme, puis fait un commit (succès) ou un rollback (échec).

trait UnitOfWork {
  def execute[R, A](effect: ZIO[R & Transaction, ApplicationError, A]): ZIO[R, ApplicationError, A]
}

Remarquez le type : execute retire Transaction de l’environnement. Le compilateur empêche donc d’appeler un repository en dehors d’une transaction.

Dans les entrypoints, la méthode authorise (voir EntrypointDsl) ouvre la transaction, vérifie les droits, puis exécute la logique métier :

override def deleteComment(request: DeleteCommentRequest): Result[DeleteCommentResponse] =
  authorise(request):     // transaction + vérification des droits (CommentAuthorisation)
    for {
      commentId <- validation.parse(request).validOrFail
      deleted   <- comments.delete(commentId) ?! NotFound.comment(commentId)
    } yield DeleteCommentResponse(deleted.id)

Il existe deux implémentations : PostgreSQL (PostgresUnitOfWork) et en mémoire (InMemoryUnitOfWork), utilisée pour les tests des services et le mode inmemory.

7 Doobie : requêtes SQL

Les repositories PostgreSQL écrivent leurs requêtes en SQL avec l’interpolateur sql"..." :

override def find(commentId: CommentId): Result[Option[Comment]] =
  PostgresTransaction.execute:
    sql"""SELECT c.id, c.article_id, c.body, c.author_id, c.created_at, c.updated_at
         |FROM comments c
         |WHERE c.id = $commentId"""
      .stripMargin
      .query[Comment]   // chaque ligne est convertie en Comment, dans l'ordre des colonnes
      .option           // 0 ou 1 ligne
  • $commentId n’est pas une concaténation de chaîne : c’est un paramètre de requête préparée (pas d’injection SQL possible).
  • .query[A] puis .option (0 ou 1 ligne), .unique (exactement 1 ligne) ou .to[List] (toutes les lignes).
  • PostgresTransaction.execute exécute la requête dans la transaction courante et renvoie un ZIO.
  • PostgresTransaction.withTime(now => ...) fournit en plus l’heure courante, pour created_at / updated_at.

Le schéma de la base est dans src/main/resources/migrations/schema (migrations Flyway). Pour modifier le schéma, ajoutez un nouveau fichier V2__....sql plutôt que de modifier V1__conduit.sql.

8 ZIO HTTP : routes

Les routes sont dans application/http/route. Chaque route associe une méthode et un chemin à un handler qui renvoie un ZIO :

literal("api/articles") / Routes(
  DELETE / string("slug") / "comments" / long("id") -> handler { (slug: String, id: Long, request: Request) =>
    for {
      user <- auth.authenticated(request)                                // utilisateur connecté, sinon erreur
      _    <- logic.deleteComment(DeleteCommentRequest(user, slug, id))  // appel du domaine
    } yield Response.status(Status.NoContent)
  },
)
  • string("slug"), long("id") : paramètres du chemin, passés au handler
  • auth.authenticated(request) / auth.anyone(request) : lit le token JWT ; anyone accepte aussi les utilisateurs non connectés (User.Anonymous)
  • parser.decode[XyzRequest.Payload](request) : lit le corps JSON
  • Response.json(result.asJson.toString) : sérialise la réponse avec Circe (codecs dans JsonCodecs)

10 ZIO Test

10.1 Structure d’un test

object CommentEntrypointServiceSpec extends ZIOSpecDefault {

  def spec = suite("CommentEntrypointService")(
    test("adds a comment to an article") {
      for {
        fixture  <- givenArticle
        service  <- ZIO.service[CommentEntrypointService]
        response <- service.addComment(addComment(fixture.profile.id, fixture.slug, "Nice article!"))
      } yield assertTrue(
        response.comment.body == "Nice article!",
        !response.comment.author.following,
      )
    },
  ).provide(                             // layers fournis aux tests
    CommentEntrypointService.layer,
    CommentValidationService.layer,
    CommentAuthorisationService.layer,
    InMemoryRepositoryModule.layer,      // repositories en mémoire : rapide, pas de Docker
  )
}
  • Un test est lui-même un ZIO : on utilise une for-comprehension et on termine par assertTrue(...).
  • assertTrue accepte plusieurs conditions et affiche clairement celle qui échoue.
  • Pour tester un cas d’erreur, .flip transforme l’erreur en succès :
test("fails with NotFound when the article does not exist") {
  for {
    service <- ZIO.service[CommentEntrypointService]
    unknown  = ArticleSlug("unknown-article")
    error   <- service.addComment(addComment(userId, unknown, "Nice article!")).flip
  } yield assertTrue(error == NotFound.article(unknown))
}

10.2 Générateurs

Generator (src/test/scala/.../entity/Generator.scala) produit des données de test aléatoires avec Gen :

def userName: Gen[Any, UserName] = Gen.stringBounded(3, 20)(Gen.alphaChar).map(UserName(_))

userId <- Generator.userId.runHead.someOrFailException   // une seule valeur aléatoire

On peut aussi vérifier une propriété sur beaucoup de valeurs générées avec check (tests par propriétés) :

test("a valid body is accepted") {
  check(Gen.stringBounded(3, 500)(Gen.alphaChar)) { body =>
    assertTrue(CommentBody.fromString(body).toEither.isRight)
  }
}

10.3 Tests des repositories PostgreSQL

Les specs de infrastructure/postgres/repository utilisent une vraie base PostgreSQL dans Docker. Chaque test s’exécute dans une transaction (transaction:) sur une base recréée (@@ withMigration) :

test("Adds a comment and retrieves it") {
  transaction:
    for {
      ...
      created <- comments.save(comment)
      fetched <- comments.find(created.id)
    } yield assertTrue(fetched.contains(created))
} @@ withMigration
